Lottery Day: the Explained Lottery

Turn the most anxious moment in a family's journey into the most trust-building one — and close the real gap where non-selected families currently hear nothing.

PLAN — READY FOR STEP-BY-STEP EXECUTION July 2026·Written to be executed phase-by-phase by any capable model

1Why this is the next big feature

  • It's imminent. C.R. Neal holds 1,263 leads against a founding class of ~150–200 seats. If even a fraction converts, the lottery will run — and lottery day becomes the single highest-stakes family touchpoint before school opens.
  • There's a real product gap, verified in code. Today, finalizing a lottery creates offers for winners — and nothing for everyone else. Non-selected families sit at status lottery_assigned in silence until staff manually waitlist them one at a time. Phase LD-3 closes this loop.
  • No vendor does this. Research on New Orleans' OneApp showed families' anger came from opacity, not outcomes — the algorithm worked; nobody explained it. SchoolMint and Avela run compliant lotteries; neither explains a family's result to them. This is the most Rooted-shaped feature on the roadmap: transparency as equity.
  • It's cheap relative to its weight. Every hard part already exists — seeded reproducible lottery, tiers, snapshots, live waitlist positions, bilingual notify/email/SMS rails. This feature is mostly assembly and language.

3Phases — step-by-step for the executing model

Global guardrails for every phase (non-negotiable): ❶ Never modify packages/utils' runDeterministicLottery or generateLotterySeed — the audit trail depends on them. ❷ Every user-facing string gets EN + ES entries in apps/web/lib/i18n/translations.ts; family emails use the bilingual renderEmail pattern in lib/email-templates.ts. ❸ Copy existing patterns — notify fan-outs from lib/notify.ts, public pages from app/(public)/inquire/page.tsx (LocaleProvider wrapper), service-role reads only after RLS-proven ownership (see getWaitlistStandings in lib/queries/family.ts). ❹ New DB changes = numbered migration file in supabase/migrations/ AND applied to prod project szockdlohlmkyloubgtd via Supabase MCP. ❺ Verify each phase: npx tsc --noEmit && npx vitest run && npx next build in apps/web; commit per phase with the Co-Authored-By line; push and confirm CI.

LD-1 · The public explainer (smallest, ship first)

  1. Create app/(public)/how-the-lottery-works/page.tsx — server component, dynamic = "force-dynamic", wrapped in LocaleProvider with getLocale() (copy the inquire page shell exactly).
  2. Content sections: what a lottery is and when it runs · the 4-step timeline (apply → draw → priority order → offer/waitlist) · priority groups rendered per campus from the live lottery_rule_set.priority_tiers (service-role read; fall back to the sibling-only default in lib/mutations/lottery.ts) · the three promises (reproducible, untouchable, live position) · FAQ accordion (6–8 questions) · Apply CTA.
  3. All copy via new lottery.* translation keys — bilingual, 6th-grade reading level, no jargon ("random number," never "deterministic seed" in family copy).
  4. Link it from: the landing page hero area, the inquiry thank-you card, and the applicationReceived email template (one added sentence + link).
ACCEPT: /how-the-lottery-works renders both languages via the toggle; tier list shows C.R. Neal's actual rule set; page is linked from all three entry points; build green.

LD-2 · The family result experience

  1. New query in lib/queries/family.ts: getLotteryOutcome(applicationId) — RLS-proven ownership first (user client fetches the application), then service role reads the matching lottery_entry_snapshot row + run stats (total applicants, total seats, tier label) + current waitlist_position effective rank (reuse getWaitlistStandings math).
  2. New page app/family/lottery/[applicationId]/page.tsx per Mock A: result header, the numbers card, "What happened" in plain language (tier + draw framing), "What happens next" (offer deadline / live position / how the line moves), and a collapsed "Verification details" section (run date, seed fingerprint — first 8 chars — and the child's random number).
  3. Family dashboard (app/family/dashboard/page.tsx): waitlisted cards gain a "See what happened →" link to the new page; offered cards keep routing to the existing offer flow.
  4. Do not build a new notification here — LD-3 owns notification.
ACCEPT: a waitlisted family can open their result page and see tier, applicants, seats, live rank, and next steps in either language; a family that was never in a lottery gets a graceful empty state; ownership enforced (another family's applicationId 404s).

LD-3 · Close the loop on finalize (the real gap)

  1. New mutation in lib/mutations/lottery.ts: completeLotteryResults(runId, actorId) — for every snapshot with is_selected = false, in final_rank order: ensureWaitlist for the run's campus/grade/year, then create the waitlist_position (position = rank order), set application status waitlisted, and audit-log. Idempotent: skip applications already holding an active waitlist_position or offer. Follow the existing addToWaitlist shape.
  2. Upgrade notifyFamilyApplicationWaitlisted in lib/notify.ts to full fan-out: in-app + bilingual email (new template lotteryResultWaitlisted with position + link to the LD-2 page) + consented SMS. These are transactional — exempt from marketing suppression, matching the offer notifications.
  3. Call it from completeLotteryResults per family, sequentially (hundreds of sends is fine — mirror the campaign cron's per-recipient loop, no new pacing infra).
  4. Staff UI (app/staff/lottery/[id]/lottery-detail-client.tsx): on an official run, next to "Send Offers," add "Waitlist & notify non-selected (N)" with a confirm dialog stating exactly what will send. Show completion state after.
ACCEPT: after finalize + both buttons, zero applications remain in lottery_assigned; every non-selected family holds a waitlist position matching their lottery rank and received in-app + email (+ SMS if consented); re-clicking sends nothing twice.

LD-4 · The transparency artifact (authorizer-grade)

  1. New route app/staff/lottery/[id]/report/page.tsx: a print-styled (@media print) run report — campus, grade, run number, executed-by/at, seed fingerprint, per-tier applicant/seat/offer/waitlist counts, snapshot count, and a plain-English methodology paragraph. No student names on the default view; a "with names" toggle for internal audit only.
  2. "Print / Save PDF" button (window.print) + link from the lottery detail page.
  3. Decision-gated (see §4 D3): optional anonymized public summary block on /how-the-lottery-works listing completed runs ("Grade 6 · June 1 · 212 applicants · 50 seats").
ACCEPT: staff can produce a one-page printable report for Voorhees/authorizer for any official run; numbers reconcile exactly with snapshots.

4Key decisions (defaults chosen — override before build)

  • D1 — Show the child's raw draw number? Default: yes, but only inside the collapsed "Verification details" section. Headline is always tier + place in line, which is what families can act on.
  • D2 — Auto-waitlist on finalize? Default: no silent automation — one explicit staff button with a confirm dialog ("this will notify 162 families"). Lottery day deserves a human on the trigger.
  • D3 — Public anonymized run summaries? Default: build behind a flag, ship off. Steven decides with the authorizer; counts-only summaries are strong trust signals but set a precedent.
  • D4 — SMS on results? Default: yes for consented families (transactional). It's the single message most worth a text.
  • D5 — Where the explanation lives: dedicated page (/family/lottery/[id]), not a modal — it's linkable from email, printable, and calm.

5Risks

  • Copy is legally load-bearing. "Nobody can move a child up the list" and tier descriptions must match the authorizer-approved policy exactly. Mitigation: Lalah + authorizer review the explainer copy before LD-1 publishes; tiers render from the live rule set, never hardcoded prose.
  • Position visibility can cut both ways. #4 feels hopeful; #87 feels crushing. Mitigation: below ~top-20, lead with "on the waitlist" framing and historical movement language rather than the raw number headline (number still available).
  • Notification burst on lottery day. Hundreds of simultaneous transactional emails is fine for Resend, but a bad template ships at maximum blast radius. Mitigation: mandatory send-to-self test on the new template + a 5-family pilot batch option in the confirm dialog.
  • Timing. This must land before C.R. Neal's lottery date — LD-1 and LD-3 are the must-haves for that day; LD-2 and LD-4 can trail by days if needed.
  • Rule-set drift. If a campus edits tiers after a run, the explainer and the historical result must not disagree — result pages read the run's snapshot, never the current rule set.
